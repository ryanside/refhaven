# refhaven decisions

The rules for working in this repo. refhaven is a reference library for images. You save images into a library, which you browse as a gallery, and gather them into collections. A collection opens as its canvas, a free arrangement, and has a gallery too. Agents will read and save references through a CLI and an MCP server.

The [README](../README.md) covers how to run the project, the checks, and the layout.

## How to read a row

| State | Meaning |
|---|---|
| Built | The code does this today. |
| Planned | Decided, and not built yet. Build it this way. |
| Later | Not decided in detail. The row gives the starting point. Confirm it with the owner when you build that part. |
| Open | The owner has not decided. Ask before you build on it. |

"Lock" marks a rule that is painful to change once there is real data.

## Stack

TanStack Start with React, Tailwind 4, and shadcn on Base UI (preset `b1VlJAwK`). Convex with Confect, so backend code is written with Effect 4.1. Convex Auth 2.0. Cloudflare R2 through Convex's R2 component. PixiJS 8. Bun and Turborepo. TypeScript 7. Every version is an exact pin, and the shared ones live in the Bun catalog in the root `package.json`.

## Working rules

Each rule below comes from a bug or a wrong assumption already hit in this repo.

### Backend

- Write backend code in `packages/backend/confect`. `confect codegen` owns `convex/` and `confect/_generated/`, and it deletes any file in `convex/` that it did not write. The two exceptions are `convex/convex.config.ts` and `convex/tsconfig.json`.
- A table is one file in `confect/tables/`. A function group is a `*.spec.ts` and `*.impl.ts` pair. A spec is bundled into the browser, so it must not import server code.
- `confect/auth.ts` is the Convex auth config. The sign-in functions that Convex Auth returns are plain Convex functions, and they live in the `session` group.
- Every group that acts for a user attaches the `RequireWorkspace` middleware and reads the user and workspace from `CurrentWorkspace`. Never take a user ID or a workspace ID from a function's arguments.
- An action that calls a function gets that function's declared `error` as typed errors. Declare the error on the called function and pass it on, as `library.save` does with `record`. An undeclared error reaches the caller as a defect.
- Sign R2 URLs in a mutation or an action, never in a query. Convex caches query results, so a query returns the same signed URL after it has expired.
- Name unit tests `*.test.ts`. Confect's specs are named `*.spec.ts`, and Vitest must not run them.

### Web

- Signed-in routes live under `_app` and set `ssr: false`. The session tokens are in `localStorage`, because Convex Auth's cookie mode is for Next.js only.
- Load every image as a CORS request. An `<img>` sets `crossOrigin="anonymous"`. A response cached from a plain `<img>` has no CORS headers, and a later canvas load of the same URL fails on it.
- Do not subscribe to every item of a canvas with one live query. It resends every item on each change. See C19.
- Call Confect functions with the hooks from `@confect/react`. Use TanStack Query only for data that is not a live Convex subscription.
- The UI stays plain. Use the shadcn preset's defaults and no custom styling until the design pass.

### Git

- Open a pull request for anything beyond a simple, high-confidence change. Push a simple, high-confidence change straight to `main`.
- Whoever opens a pull request watches it and merges it once CI is green. Merge a stack bottom-up with merge commits, so the branches above need no rebase.
- CI runs the typecheck, lint, the format check, and the unit tests on `main` and on every pull request. The browser checks need the dev deployment and R2, so they run locally, through the `verify-refhaven` skill.

### R2

- The bucket is private. Its CORS policy lists the app's origin, the methods `GET` and `PUT`, and the headers `Content-Type` and `x-amz-checksum-sha256`.
- R2 checks an upload's SHA-256 only when the hash is a signed header, `x-amz-checksum-sha256`. As a URL parameter, the presigner's default, R2 ignores it.
- The Convex deployment needs `R2_BUCKET`, `R2_ENDPOINT`, `R2_ACCESS_KEY_ID`, and `R2_SECRET_ACCESS_KEY`. `R2_ENDPOINT` is the account URL, `https://<account-id>.r2.cloudflarestorage.com`, with no bucket name after it.

### Sign-in

- Passkeys are bound to their `rpId` for good. `AUTH_RP_ID` and `AUTH_ORIGIN` on the Convex deployment set it, and they default to `localhost` and `http://localhost:3000`. Set both before the first real user signs up.

## Product model

| ID | Rule | State |
|---|---|---|
| B1 | The library is everything you have saved. Each saved thing is a Ref. | Built, lock |
| B2 | A collection is a named set of Refs. A Ref can sit in many collections, and in each at most once. A name is trimmed and then 1 to 100 characters, and two collections may share one. Deleting a collection waits for C15. | Built, lock |
| B3 | A gallery and a canvas are views, not things, and only a collection has both. The library is shown as a gallery only. A collection opens as its canvas, which holds its layout, notes, and groups, and its gallery is its second view. A filter of the library or of a collection, by search text and tag, exists in the gallery view. `library.filter` returns it, and the page shows it with the same cards as the full gallery. A collection's canvas ignores the filters, and dimming the items a filter leaves out waits for B11. Both galleries use one component and one item shape. | Built, lock |
| B4 | A canvas is the canvas view of one collection. There are no separate boards, and the library has no canvas. A canvas row names its collection in `collectionId`, and `canvas.open` requires one. `/c/{collectionId}` shows the canvas, and `/c/{collectionId}?view=gallery` the gallery. A canvas row with no `collectionId` is the canvas of a library from before this rule. The dev deployment keeps one for nearly every workspace, with its items. No canvas function reads or writes it: `canvas.changes` and `canvas.apply` refuse it with `CanvasNotFound`, as they refuse a missing canvas. The trash and the purge still reach its items through `by_ref`, as they do every canvas's (C15): a delete or a restore raises the row's `rev` and stamps its items, and the purge deletes them. | Built, lock |
| B5 | Each collection keeps one saved layout. A workspace has at most one canvas per collection, found by the index `by_workspace_and_collection`. A move on one canvas does not change another. | Built, lock |
| B6 | An item dropped on the canvas lands where you dropped it. An item added anywhere else is placed beside the existing layout the next time the canvas opens. `canvas.open` places each Ref that has no item in rows to the right of the layout, 40 units away, with its longer edge at 400 units. Image files dropped on a canvas are saved, and each is placed with one `add` op of `canvas.apply`: the first centered on the drop point, and each next one of the same drop 440 units, the longer edge plus the gap, to the right, so they never overlap. A pasted image, one picked with `Add images` in the canvas's panel, or a file dropped beside the canvas, as on that panel, starts at the center of the view. The item shows when `canvas.changes` reports it. There is no placeholder while an image uploads. | Built |
| B7 | An image is in a collection exactly when it is on that collection's canvas. Removing an image from a canvas takes it out of that collection, and it stays in the library. A removal and `collections.removeRefs` both go through `leaveCollection` in `confect/membership.ts`, which deletes the membership and marks the item removed, so the canvas shows only members. A save into the collection, `collections.addRefs`, and an `add` op of `canvas.apply` make a Ref a member through `addMember`. When a Ref is added to the collection again, `open` revives its item under the same key, beside the layout, and an `add` op brings it back at the point it names, which is how undo restores a removal. `open` returns `placed`, the number of items it put on the canvas, which are the last items of its list. The canvas page removes the selected items with Delete, Backspace, or `Remove from collection`, as one `canvas.apply` call of `remove` ops. Removal is not optimistic: the items leave when `canvas.changes` reports it. | Built |
| B8 | A canvas holds one item per Ref. | Built |
| B9 | Notes and groups live on the canvas and not in the library. A note is an item of one canvas and nothing else: no Ref, no membership, and no place in a gallery or in search. A group is the same: an item of one canvas, with no Ref and no membership. Removing a group touches no collection, and the trash never touches a group or a `parent`. Notes and groups exist. | Built |
| B10 | A collection's canvas opens whole. Loading thousands of items in pieces comes with the speed work. Until then `canvas.open` reads every membership of the collection, the Ref of each, and every item of the canvas in one transaction, plus one Blob for each image it places. A Convex transaction allows 4,096 reads, so the first open of a collection is good to about 1,300 images. That size is worked out from the limit, not measured. The library has no canvas, so no call reads the whole library onto one. | Later |
| B11 | On a collection's canvas, a filter dims the items that do not match. The library has no canvas, so this is about a collection's canvas only. It waits for the owner. | Later |

## Data

| ID | Rule | State |
|---|---|---|
| C4 | Every document carries `workspaceId`. Each user gets a personal workspace at sign-up. | Built, lock |
| C5 | The tables are Workspace, Blob, Ref, Collection, CollectionRef, Tag, Canvas, and CanvasItem. A CollectionRef row is one Ref's membership in one collection, and `by_ref` lists the collections of a Ref. A Tag row is one tag on one Ref: `workspaceId`, `refId`, and `name`. A Ref has a tag at most once. `by_ref` lists a Ref's tags in the order added, and `by_workspace_and_name` lists the Refs of one tag and the workspace's tag names. A tag's name is trimmed, inner runs of spaces become one space, and it is lowercased, so "Mood", " mood ", and "MOOD" are one tag. It is then 1 to 50 characters. `TagName` in `confect/refFields.ts` holds that rule for the page and the server. Lowercase tags are a default the coordinator chose, and the owner can still change it. `ref.tags` reads every tag row of the workspace in one range, the tags of images in the trash too. Convex scans at most 32,000 documents in a transaction and returns at most 8,192 elements in an array, so it is good to about 32,000 tag rows and 8,192 distinct names in a workspace. That size is worked out from the limits, not measured. A tag has no `source` yet. See T4. | Built, lock |
| C6 | A Blob is bytes keyed by SHA-256 inside a workspace. A Ref points at its original Blob, in `blobs.original`. The Blob records its variants, a thumbnail and a display copy, because they derive from its bytes. Every Ref that shares the Blob shares them. A page asks for a role, original, thumbnail, or display, and gets the variant when the Blob has it and the original otherwise. | Built, lock |
| C16 | A Ref records its file name, an optional note, and an optional source URL, and its creation time is the upload time. An absent note or source means none, and none is never stored as an empty string. A file name is trimmed and 1 to 255 characters. A note is trimmed and 1 to 10,000 characters. A source is trimmed, at most 2,048 characters, and parses as a URL with the protocol `http:` or `https:`, so a `javascript:` or `data:` link is never stored. The argument schemas of `ref.update` and `library.save` enforce these rules on the server, from `confect/refFields.ts`, and the page checks them first. The Blob records the hash, byte size, MIME type, pixel size, ThumbHash, and the byte size and pixel size of each variant, because they describe the bytes. A Ref also stores `searchText`, derived from its name, note, source, and tags for E6. | Built, lock |
| C8 | IDs are Convex document IDs. A canvas item also carries a `key`, unique inside its canvas. An image item's key is always its Ref's ID, whether `canvas.open` or an `add` op made it, so a canvas cannot hold two items for one Ref and `leaveCollection` finds an item by its Ref. A note's key is made by the client, with `crypto.randomUUID()`, so the page shows a new note before the server answers. A key is 1 to 64 characters and unique on its canvas: an `addNote` op under the key of a live item, or of a removed image, fails with `KeyTaken`. Nothing stops a client from naming a note with the ID of one of its own Refs that has no item yet. That note would then block the image of that Ref on that canvas. The web app never does it. A group's key is made the same way, and an `addGroup` op under the key of a live item, or of a removed item of another kind, fails with `KeyTaken`. | Built, lock |
| C15 | A delete is a soft delete with a 30-day trash. A Ref with a `deletedAt` is in the trash. Every reader derives what it shows from that one field, through `isLive` and `liveRefs` in `confect/ref.ts`, and `canvas.changes` sends it as the item's `deletedAt`. `library.remove` and `library.restore` write only the Ref, plus a new `rev` on each of its shown canvas items, so `canvas.changes` reports the item removed and back. Memberships and items keep their rows, so a restore puts the image back in its collections and at its place on each canvas. `/trash` lists deleted images with a `Restore` button, says that images there are deleted for good 30 days after they were deleted, and shows each card's days left, from `daysLeft` in `confect/trash.ts`. The purge is two steps a week apart, in the `trash` group, each run by a daily cron job (I6). `trash.purge` deletes each Ref whose `deletedAt` is more than 30 days old, with its tags, its memberships, and its items on every canvas. One mutation takes up to 50 Refs and deletes at most 500 of the rows that point at them, far inside Convex's limit of 16,000 writes, and the action repeats it until none is left. A Ref goes whole when it can: one whose rows may not fit in what is left of a mutation waits for the next. Only a Ref with 500 rows or more is cut. It keeps its own row, and the next mutation goes on with it, at once or on the next day's run if the action died. A restore of that Ref in between would bring it back without the rows already deleted. When no other Ref, live or in the trash, points at its Blob (`by_blob`), the same mutation deletes the Blob row and writes an `orphans` row in its place: the workspace, the hash, the upload, the variants the Blob had, and the time. Nothing leaves R2 in that step. `trash.sweep` takes the orphan rows more than 7 days old, 50 at a time, in three steps. A mutation returns each row's object keys. The action deletes those objects from R2. A second mutation deletes the rows. A sweep that dies in between leaves its rows, and the next day's deletes what is left: deleting a missing object is not an error. An object's key holds its upload's ID (H4), and no two uploads share one, so the keys of an orphan row are never used again. A save of the same bytes after the purge is a new upload under new keys, and the old objects go at their sweep all the same. So no delete can reach bytes that a Blob row names, however late R2 applies it, and a save takes no lock against the sweep. `library.save` reads which upload holds the bytes, looks at that upload's objects in R2, and then records them. `record` goes on only while the Blob row still names that upload, or, with no Blob row yet, while the upload row still waits. A purge between the look and the record deleted the Blob row, so that save fails with `UploadNotFound` and writes nothing, and saving again works, as a new upload. The page meets this when the purge runs between its `prepareUpload`, which offered no upload because the Blob row was there, and its `save`. The sweep's first mutation still reads the Blob row of each orphan row's bytes, because a wrong delete cannot be undone: a row whose upload a Blob row names is deleted, and its objects stay. No save can bring that about. Rows from before uploads had IDs can be in that state, because their keys hold the hash alone. Both functions take `pretend`, a time to treat as now together with one workspace, or nothing, which means the real clock and every workspace. A pretend time with no workspace cannot be expressed. `check:purge` always names its own workspace. Running either function by hand with `pretend` and the owner's workspace purges and sweeps their trash early, and that is the one way left to lose real bytes. What remains open is rows and objects that nothing collects. A page that asked for an upload and never saved leaves its `pendingUploads` row, and its objects if it sent any. So does a save that fails after its upload, as with a file that is not an image. A later save of the same bytes uses that row and those keys. A variant uploaded for a Blob row by a save that then failed is in no row, so it stays in R2 after that Blob's sweep. So does an object uploaded under an old-form key and never saved before uploads had IDs. | Built |
| C17 | The URLs are `/library`, `/c/{collectionId}`, and `/r/{refId}`. On `/c/{collectionId}`, `view` is `canvas` or `gallery` and defaults to `canvas`, and two links in the title bar, `Canvas` first, switch between the views. `/library` is a gallery and ignores `view`: `/library?view=canvas` shows the gallery. `/r/{refId}` is one image's page. It shows the 2048 px copy, the pixel size and type, and a link to the original. It saves the name, the note, and the source each on its own submit, adds and removes tags, lists the image's collections, and deletes or restores the image. It reads `ref.get`, which answers for a Ref in the trash too. `ref.update`, `ref.addTags`, and `ref.removeTags` refuse a Ref in the trash with `RefNotFound`. A missing Ref and another user's show `Image not found.` The image on every gallery card, the trash's included, links to the page. The canvas does not link to it yet. | Built, lock |
| C18 | Export is a zip with `manifest.json` and the original files. | Later |
| I7 | One helper resolves the caller's workspace, and every function uses it. It is the `RequireWorkspace` middleware. Scopes join it with API keys. | Built, lock |
| I5 | The CLI and agents call a Confect HTTP API inside Convex, which runs the same functions as the browser. | Planned |
| I6 | Background jobs use Convex's scheduler and cron. `search.backfill` schedules its next page with the scheduler. `confect/crons.ts` declares the two daily jobs of C15: `trash.purge` at 09:00 UTC and `trash.sweep` at 09:30 UTC. Neither passes an argument, which means the real clock and every workspace. Convex runs one run of a job at a time. `convex dev` pushes the jobs to the dev deployment like any function, so they run there for real. | Built |

## Storage and images

| ID | Rule | State |
|---|---|---|
| H3 | Originals are kept byte-exact. | Built, lock |
| H4 | Object keys are `w/{workspaceId}/o/{sha256}/{uploadId}` for an original and `w/{workspaceId}/v/{sha256}/{uploadId}/{file}` for a variant. A variant's `{sha256}` and `{uploadId}` are the original's, and `{file}` is `512.webp` or `2048.webp`. `{uploadId}` is the ID of the `pendingUploads` row that `prepareUpload` writes for bytes the workspace has no Blob row for. Until a save records them, every `prepareUpload` of those bytes gets the same row. `record` deletes the row and writes its ID into the new Blob row. Convex gives no two rows one ID, so no key is used for a second upload, and nothing can delete bytes saved again by deleting the key they had before (C15). A Blob saved before uploads had IDs has none, and its keys are the same without `/{uploadId}`. | Built, lock |
| H5 | Bytes are de-duplicated per workspace, never across workspaces. | Built, lock |
| H6 | The browser uploads straight to R2 through a signed URL. The server makes the object key from the workspace, the hash, and the upload's ID (H4). An original's URL is signed for its hash, so R2 stores no other bytes under that key. After the upload the server reads the object's size and first 12 bytes from R2 before it records anything. | Built |
| L1 | The server records the file type that the bytes show and ignores the client's claim. | Built |
| D18 | The formats are PNG, JPEG, WebP, GIF, and AVIF. SVG is rasterized at upload. The server refuses SVG until the rasterizing step exists. Variants are WebP, and the server refuses a variant whose bytes are not WebP. | Built |
| H7 | An image is at most 50 MB. The server checks the size when the image is saved, after the upload. | Built |
| E5 | Saving bytes the library already holds reuses the Blob, uploads the original no second time, and tells you. It adds a second Ref. It also adds any variant or ThumbHash the Blob still lacks. | Built |
| H10 | Images are served through signed R2 URLs. A mutation signs each URL for one hour, for the role the page asks for, and the page asks for a new one after 50 minutes. The gallery asks for the thumbnail. The canvas asks for the thumbnail or the display copy by each image's size on screen. | Built |
| L2 | The server checks the workspace before it signs a URL. | Built |
| H8 | An image gets a 512 px WebP thumbnail when its longer edge is over 512 px, and a 2048 px WebP display copy when it is over 2048 px. A variant keeps the aspect ratio, and its longer edge is the role's edge. Every image gets a ThumbHash, which the gallery shows until the thumbnail loads. An image saved before variants existed has none and is served from its original. | Built |
| H9 | The browser makes the variants and the ThumbHash at upload. A browser that cannot encode WebP, such as Safari, saves the original alone. For a CLI or agent save, the app makes them the first time it shows the image. There is no server image code. Only the browser part exists. | Built |
| L4 | A save from a URL fetches http and https only, with a cap on size and time. | Planned |

Known gaps in the upload path:

- A variant's upload URL is bound to no hash, because the browser makes the variant. The URL stays valid for 15 minutes, so a client can replace its own variant after the server read it.
- A retried save adds another Ref, because nothing identifies one save attempt. The web app never retries. Give each save a client-made ID before the CLI or an agent saves.
- An upload that is too large, refused, or abandoned stays in R2 with no Blob. The same holds for a variant.
- A new signed URL makes the browser download the image again, so an open page reloads its images about once an hour. Signing with a rounded date gives a URL the browser can cache.

## Canvas

| ID | Rule | State |
|---|---|---|
| C19 | Each canvas document carries a revision counter. A mutation raises the counter once and stamps the items it wrote. The client loads a snapshot with `canvas.open`, then subscribes to `canvas.changes` for the items written after the snapshot's revision. The client takes a new snapshot on every page load and when the change list passes a set size. A snapshot must not outlive the trash period of C15, or a purged item comes back. The canvas page takes a new snapshot when the change list passes 200 items. The purge deletes a purged image's items as rows and raises no rev, because every canvas reported them removed when the image went to the trash, and a page that heard it dropped them. A page that did not hear it, because it stayed open with no connection from before the image's delete until after its purge, has no change that removes the item. It keeps showing it from its snapshot until a reload or 200 changes, and its next `library.urls` call that names the image fails with `RefNotFound`. The lab that measured this design is in git history. | Built, lock |
| C7 | A canvas item is a tagged union of image, note, and group, with `kind` as the tag. Every item has a key and a `deletedAt`. An image and a note also have a place, a scale, a rotation, a `z`, an optional `parent`, and a `width` and `height` that are their size at scale 1. A group has nothing else: no place, no size, no `z`, and no `parent`. An image item points at a Ref and copies the pixel size of its original, so a client can hit-test with no join. A note item has `text`, `color`, and its box in world units, and no Ref. `CanvasItem` in `confect/canvasItem.ts` is that union for the functions. The `canvasItems` table is the same union with the row fields added, which Confect 10.6 compiles to a Convex `v.union` of three objects, so a note with a Ref, an image with text, or a group with a place cannot be stored. `parent` is optional, so the rows from before groups stay valid with no migration. The `by_ref` index lists images only. A patch may set only the fields of its item's kind, from `patchable`, or the call fails with `FieldNotOnItem` and writes nothing. A group takes no field, so any patch of a group fails. The `addGroup` op takes only a key, so a group with a place, a Ref, or a parent fails the argument schema. Images, notes, and groups exist. | Built, lock |
| C9 | A canvas stores one document per item. | Built, lock |
| C10 | An edit is saved as one mutation per gesture, carrying a list of item operations. `canvas.apply` takes up to 1,000 patch, remove, add, addNote, and addGroup operations, in any mix. An addNote names a note's key, place, scale, rotation, text, color, and box, and an optional `z`. It inserts the note, or brings back the removed note under that key with those values, which is how undo restores a removed note. A remove of a note touches no collection. The page sends a larger edit as several calls, one after the other, so a move or a removal of more images than that is not one transaction. A patch or remove on a missing or removed key fails the whole call with `ItemNotFound`, and nothing is written. An add names a Ref and a point. It inserts the Ref's item with its longer edge at 400 units, brings a removed one back, or moves a live one. Each of the three takes a z above every item, unless the add names a `z`, which undo uses to restore a removed item's place in the stack. It also makes the Ref a member of the canvas's collection, through `addMember`. An add of another workspace's Ref, a missing Ref, or a Ref in the trash fails the whole call with `RefNotFound`. To find the top z, a call with an add that names no `z` reads every item of the canvas once. A call whose adds all name a `z` does not. | Built, lock |
| C11 | Each operation patches only the fields it changed, so the last write wins per field. | Built |
| C12 | An item has x, y, uniform scale, rotation, flip, crop rectangle, opacity, and grayscale. They are stored on the item and never baked into pixels. The server refuses a scale of 0 or less, an opacity outside 0 to 1, and a number that is not finite. Crop joins with the feature that sets it. The page sets x, y, scale, and rotation. A resize changes the scale only uniformly, so an image keeps its aspect ratio. Flip, opacity, and grayscale have no control yet. | Built, lock |
| C13 | Z-order is a fractional index string per item, from `fractional-indexing` 4.0.0. The server refuses a z that is not a valid key, because the next key above it could not be made. Items with the same z are ordered by key. `stackOrder` in `packages/scene` is that order, and the renderer and the hit test both use it. "Bring to front" and "Send to back" give each selected item a new z from `zAbove` or `zBelow`, above or below every item of the canvas, and keep the selection's own order. Each is one `canvas.apply` call with one patch of `z` per item, or several calls when the selection holds more than 1,000 items (C10), and one undo entry. A command with nothing selected, or a selection already at that end in its order, makes no call. Stepping one level up or down does not exist, and a click does not raise an image. | Built, lock |
| C14 | A group is a parent reference on its items. An image or a note may carry `parent`, the key of a group on the same canvas, and it is in that group while the group is on the canvas. A group holds no list of members, and has no parent, so there is one level and an item is in at most one group. An `addGroup` op adds a group under a client-made key, or brings back the removed group under that key, which is how undo restores one. A patch sets `parent` to a group's key, or to null to take the item out. `canvas.apply` checks once, after every op of the call, that each `parent` it set names a group of the canvas, live or removed, so one call can add a group and fill it. Otherwise the call fails with `GroupNotFound` and writes nothing. Removing a group writes its row only. Its members stay on the canvas and keep their `parent`, which counts for nothing while the group is removed. So removing a group and bringing it back are exact opposites, and a member that was out of view when the group was removed, such as one whose image was in the trash, is in the group again once both are back. A reader of `canvas.open` or `canvas.changes` takes a `parent` that names no group on the canvas as no group. Removing a member leaves its group as it is, so a group may end with one member or none. That is allowed: a group of one behaves like its one item, an empty group shows nothing, and nothing cleans it up. `canvas.open` and `canvas.changes` return group rows like any item, and a group never counts or moves in placing new Refs or in the top `z`. `leaveCollection` and the trash touch images only and keep `parent`, so a member whose image is in the trash is hidden like any trashed image and is back in its group on restore. On the page a group is one rule about selection, `grouped` in `packages/scene`: selecting any member selects every live member of its group. A click, a shift-click, a marquee, select all, and each change from the server or a held patch apply it, so the selection holds whole groups, and a shift-click on a selected member takes its whole group out. While a drag, a resize, or a turn runs, the selection stays what the gesture began with, so the frame never covers an item the gesture does not move. An item that joined one of its groups meanwhile joins the selection on release. Dragging, resizing, turning, restacking, and removing act on the selection and know nothing of groups. A group has no outline of its own, and a double click on a note in a group opens its editor. Mod+G or `Group` puts a selection of two or more items in a new group, in one call that adds the group and patches each `parent`. That is one op more than the items, so a group of 1,000 items or more is sent as several calls, like any edit over 1,000 ops (C10). An item that was in another group moves to the new one. It does nothing when the selection is already one group. Mod+Shift+G or `Ungroup` removes each group the selection holds, with one `remove` per group, sent the same way. Each is one undo entry. A grouping is undone by removing the group and giving each item the `parent` it had, which may name a removed group. An ungrouping is undone by adding each group again, with no patch. The page holds the `parent` patches and the new group, so a new group selects together at once. Ungrouping shows when `canvas.changes` reports it, like a removal. Nested groups, selecting one member inside a group, and naming a group do not exist. | Built |

The interface is set camera, upsert items, remove items, upload texture, evict texture, and draw. An item carries its size in world units, so a texture of any resolution covers the same area. | Built |
